## Live guest checks

`apps/api/test/vm-isolation.live.ts` booted a fresh overlay of the provisioned guest template. Public HTTPS succeeded; private and metadata proxy requests were rejected; direct access to a host canary was blocked, with zero canary hits. The guest's QEMU network is restricted, with a fixed relay to a public HTTP/HTTPS proxy. The private-provider configuration override does not lift bot fetch restrictions.

`apps/web/test/computer.live.spec.ts` used real QEMU, guest noVNC modules, and WebSocket traffic. It opened the preview, took control, clicked the terminal, typed a command, verified the resulting file inside the guest, and returned control. The sandboxed viewer's origin was confirmed opaque (`null`). A separate arbitration regression test verifies that taking control wins over a bot action waiting on the guest screen lock.

Run these checks with `REX_TEST_VM_TEMPLATE` pointing to a provisioned template and an unused `REX_VM_PROXY_PORT`; see the test files for setup. The normal browser suite skips the live test when no template is provided.

The live guest test also writes and reads a project through `computer_files`, rejects a path outside the bot workspace, starts a persistent static server, confirms the real HTTP title, and verifies that the title appears in the guest browser's window list. It replaces text and observes the changed HTTP source, stops the process, and starts/stops a custom server command with allocated PORT/HOST. These operations run over SSH inside a fresh VM overlay, including on the existing template without rebuilding it.

`apps/api/test/realtime.test.ts` verifies immediate message persistence, cancellation of the old model stream, updated model context, chronological partial replies, skipping obsolete tool calls after a running command completes, and switching the selected group member. `apps/web/test/realtime.spec.ts` verifies three messages through the live composer and deduplication after reload. The resulting conversation screenshot was visually inspected.

## Limits

The launcher browser tests simulate the native command bridge. Rust validation tests and actual Linux installer builds pass, but the native application's remote login flow has not been manually tested across desktop operating systems. Windows and macOS installers were not built here. No production website was deployed during this work; the server needs deployment and restart to apply the changes. Existing VMs with unrestricted network arguments restart on next use while retaining their disks.

Taking control blocks bot mouse/keyboard input while file edits, shell commands, screenshots and project servers continue. New shell commands have no DISPLAY/dbus, and project tools defer browser opening while the owner uses the screen. The desktop regression test covers this split and the live VM test confirms headless command execution, file edits, project HTTP checks, deferred browser opening and resumed opening after Return control. A command already executing may finish. Routine execution requires the API to remain running and a server-saved model connection. Bot behavior rules are instructions, not a guarantee about every model reply. Dependency audits describe currently known npm advisories, not a general security guarantee. The production web build retains its large JavaScript chunk warning.
